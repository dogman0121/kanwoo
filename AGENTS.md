# Руководство по работе с репозиторием

## Инструкции по проектам

Эти правила действуют во всём репозитории. Перед изменением сервиса прочитай его инструкции. Если задача затрагивает оба сервиса, прочитай оба файла.

- [Бэкенд Flask](backend/AGENTS.md)
- [Фронтенд Next.js](frontend/AGENTS.md)

Для совместного локального запуска выполни `bash dev.sh` из корня после настройки обоих сервисов. Параметры `--mode=backend` и `--mode=frontend` запускают один сервис.

## Как принимать решения

1. Определи ожидаемое поведение и критерий проверки. Для исправления ошибки проследи путь от точки входа до места, где поведение расходится с ожидаемым.
2. Изучи ближайший код, его вызовы и тесты. Переиспользуй принятые в проекте решения, если они подходят задаче.
3. При неоднозначности выбери обратимое решение и укажи в итоговом сообщении, какое допущение ты сделал. Уточни требования заранее, если решение меняет публичный контракт, затрагивает сохранённые данные или требует необратимых действий.

## Как вносить изменения

1. Перед внесением изменений составь пошаговый план и согласуй его. После согласования создай отдельный Git worktree и работай в нём, если пользователь не указал другое место для правок.
2. Вноси только изменения, необходимые для задачи, и сохраняй существующие правки пользователя. Для изменений на стыке сервисов проверь обе стороны API, включая форматы данных и обработку ошибок.
3. Храни секреты вне Git. Для локальной разработки и развёртывания следуй инструкциям по настройке окружения соответствующего сервиса.

## Как проверять результат

Начни с проверки изменённого поведения по инструкциям сервиса. Для сквозных изменений проверь сценарий через его обычную точку входа. Если обнаружил дефект в изменяемом поведении, добавь регрессионный тест, который воспроизводит дефект и проходит после исправления. После завершения работы повторно запусти тесты для затронутых частей проекта. В итоговом сообщении перечисли команды, сообщи, какие тесты прошли и какие завершились ошибкой. Если тесты запустить не удалось, укажи причину и что осталось непроверенным.

Покажи Git diff своих изменений прямо в итоговом сообщении, в блоке кода с языком `diff`. Если diff слишком длинный, покажи ключевые фрагменты и укажи команду для просмотра полного diff. Приведи точную команду отката, которая сохраняет правки пользователя.

## Коммиты и пул-реквесты

Пиши короткие заголовки коммитов в повелительной форме, например `Add Bash development launcher`. В пул-реквесте опиши изменение и способ проверки, приложи ссылки на связанные задачи. Отметь миграции и изменения конфигурации, а для видимых изменений интерфейса приложи скриншоты.
