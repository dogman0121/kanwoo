# Соглашения по разработке бэкенда

Порядок запуска описан в [инструкциях бэкенда](../AGENTS.md). Назначение общих компонентов и связи между модулями смотри в [архитектуре](architecture.md).

## Где размещать изменения

- Размещай предметное поведение в соответствующем модуле `kanwoo/<модуль>/`. Используй `routes.py` для Blueprints, `handlers/` для обработчиков, `schemas.py` для входных и выходных схем, `services.py` для бизнес-логики, `repositories.py` для запросов, `models.py` для ORM-моделей, а `permissions.py` для проверок доступа. Маленькие обработчики могут оставаться в `routes.py`, если так устроен модуль.
- Используй четыре пробела, `snake_case` для функций и модулей, `PascalCase` для классов. Следуй соседним DTO и схемам при именовании новых типов.
- Переиспользуй общие компоненты из `kanwoo/`. Перед изменением общего интерфейса найди его импорты и места подключения в контейнере. Выноси код на общий уровень, когда у него есть несколько предметных потребителей и одинаковый контракт.

## Организация сервисного слоя

Определяй границы сервиса по его бизнес-контексту. Учитывай назначение сервиса, сценарии, правила доступа, ограничения и инварианты бизнес-логики, а также причины, по которым сервис будет меняться.

Одна доменная сущность может использоваться несколькими сервисами, если они обслуживают разные бизнес-контексты. Например, `StudioMangaService` отвечает за управление мангой в студии, а `MangaPublicService` обслуживает публичную часть каталога.

- Объединяй операции, у которых есть общая ответственность. Принадлежности к одной сущности для этого недостаточно.
- Сохраняй у сервиса конкретное назначение. Избегай универсальных контейнеров функций.
- Разделяй сервисы при различиях в ответственности. Количество методов или строк кода само по себе не повод для разделения.
- Переиспользуй общую бизнес-логику между сервисами без дублирования.

## HTTP-контракт и доступ

- Валидируй входные данные через Marshmallow на границе HTTP. Преобразуй результат в предметный DTO, если сервис принимает DTO. Сериализуй ответ схемой и формируй его через `respond()`. Используй подходящий класс `ApiException` или предметную ошибку на его основе. Проверь HTTP-статус, `error.code` и формат `error.detail`.
- Выбирай `login_required` или `profile_required` в зависимости от того, нужен пользователь или активный профиль. Для публичного сценария с дополнительным контекстом проверь путь с `optional=True` и анонимным профилем. Проверяй право на действие над объектом через политику предметного модуля.
- Сохраняй действующий контракт списка. Для постраничной выдачи проверь `page`, `per_page` и `total_count`, для курсорной — `cursor`, `limit` и `has_more`. При изменении сортировки проверь переход между страницами с одинаковыми значениями сортируемого поля.

## Зависимости и запись данных

- Объявляй зависимости в контейнере модуля, связывай их с общими или межмодульными провайдерами в `AppContainer`. В обработчиках следуй существующему шаблону `@inject` и `Provide[AppContainer.…]`. Проверь, что выбранный провайдер объявлен и обработчик входит в подключённый пакет.
- Для новой записи через сервис используй внедрённый `DBTransaction`. Репозиторий меняет состояние сессии, граница транзакции остаётся в сервисном сценарии. Применяй `flush()`, когда идентификатор или результат SQL нужны до коммита. При использовании методов `BaseModel` проверь, где произойдёт коммит.
- Учитывай, что откат SQL-транзакции не отменяет запись файла, отправку письма или изменения в Redis. Для сценария с такими операциями продумай порядок действий и поведение при частичном сбое.
- При изменении ORM-схемы обнови миграции и проверь применение на базе с существующими данными. Команда ручного применения при запущенной локальной базе — `poetry run flask db upgrade`.

## Проверки

- Размещай `test_*.py` в `tests/unit/`, `tests/integration/` или `tests/end2end/` по уровню проверки. Используй существующие фикстуры `app`, `container`, `anonymous_client` и `authorized_client` по потребности. Фикстура приложения пересоздаёт таблицы и очищает Redis, поэтому используй отдельные тестовые БД и кеш.
- Для правок общего компонента проверь сценарий в одном из его реальных потребителей. Для регрессии доступа или формата ответа проверь HTTP-сценарий через Flask test client. Для записи проверь состояние после успешного выполнения и после ожидаемой ошибки.
- Запускай `poetry run test` из `backend/` и сверяй сводку pytest. Обёртка поднимает и останавливает Compose, но код завершения pytest не передаёт.
